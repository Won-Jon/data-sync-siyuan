## 1. 连点同步的拦截（对应反馈 ①）

| 用例 | 你做什么 | 会发生什么 |
|---|---|---|
| **TC-M2.1-01** 第二次点击被拦截 | ① 点一次同步（挑改动较多的内容，让它跑一会儿）② **立刻再点一次**（可连点几次） | 每次多余的点击只弹一条**提示**：`同步已在进行中，本次点击已忽略（右下角有进度面板）。若长时间没有进展，可重载插件后再试。`<br>**不会**再出现 `app 上已有同步正在进行中…` 的报错；**不会**出现"同步成功完成"的假提示；进度面板继续显示第一次同步的进度 |
| **TC-M2.1-02** 拦截只影响多余点击 | 等第一次同步自己跑完 | 该次同步照常给出 `同步完成`；日志里只有**一次** `Syncing with remote server app...`，多余点击不会留下日志 |

> 原理：`syncHandler` 增加 `started` 标记，被忽略的点击**不再进入**收尾的"报告/清理"逻辑（以前那条路径会写日志、清计数器，甚至弹"同步成功"）。

## 2. 同步不再卡死（对应反馈 ②，本轮最重要）

| 用例 | 你做什么 | 会发生什么 |
|---|---|---|
| **TC-M2.1-03** 深目录/多目录扫描能走完 | 设「并发请求数上限」= `1` → 同步一个结构较深的笔记本（或整库） | 面板里 `目录 i/N`、`文件 i/M` **持续前进**，最终走到 `同步完成`；**不会**停在某个数字不动（首版 M2 就是这样卡死的） |
| **TC-M2.1-04** 卡死时不再是"死锁"而是可恢复 | 同上，观察日志 | 日志里请求是**串行**的（并发 1），且同步有始有终；不存在"锁文件还在、日志没有、状态永远同步中"的情况 |
| **TC-M2.1-05** 并发上限仍然生效（回归） | 并发设 `1` → 同步；再设 `16` → 同内容同步 | 并发 1：面板"文件 i/M"逐个跳；并发 16：日志里多条 `Executing sync operation:` 连续成串，通常更快 |

**根因留档（已用 node 复现）：** 首版 M2 把"递归扫描"整体包进了同一个信号量 —— 父目录占着槽等子目录，子目录在队列里等槽，配额耗尽即**永久死锁**（实测：同类信号量嵌套 3 秒必超时）。修法：递归不再占槽，改成**每个 HTTP 请求**占槽；并把预算拆成"请求槽"与"操作槽"两个独立信号量（操作持槽等请求，同一个池才会死锁）。node 实测：10 个操作各含 2 次请求（上限 2）全部完成；8 根 × 深度 4 × 3 子的递归共 968 次请求无死锁。

### 2.1 并发 = 1 到底能不能跑（M2.2 修复）

**结论：能跑，不会死锁**（请求槽与操作槽分离，且请求之间不嵌套）。但上一版还藏着一个隐患，已修：

> `getFileBlob` 原来只是"和计时器赛跑"，**从不中止底层 fetch** —— 一次卡住的连接会一直占着并发槽。实测（上限 = 1）：超时后槽位仍被占用，后续任务被**阻塞 9310ms**（本该 100ms）。现在改为 `AbortController` 真正中止；拿到响应头后立刻停表，大文件下载不受影响。修复后实测：超时后槽位 = 0、后续任务 105ms、85KB 文件完整下载。

| 用例 | 你做什么 | 会发生什么 |
|---|---|---|
| **TC-M2.1-15** 并发 = 1 跑完整同步 | 设置「并发请求数上限」= `1` → 同步一个改动较多的库 | 能跑完（`同步完成`），只是慢；面板 `文件 i/M` 逐个跳；日志里请求严格串行。**不会**停死 |
| **TC-M2.1-16** 并发 = 1 遇到"卡住的请求"不拖死全局（关键回归） | 保持并发 `1`，把 URL 指向 `http://192.0.2.1:6806`（黑洞地址）→ 同步 | 每次超时（约 15s / 次）后**能继续重试下一次**（日志里能看到 `attempt 1/3 → 2/3 → 3/3` 依次推进）；**不会**出现"第一次超时之后整个同步再无任何日志、永远卡住"（那是修复前的表现）。测完恢复 URL |

## 3. 残留锁的处理

| 用例 | 你做什么 | 会发生什么 |
|---|---|---|
| **TC-M2.1-06** 本机自己残留的锁会被接管 | ① 读出电脑端 `data/.siyuan/sync/instance-id` 的内容 ② 手工新建 `data/.siyuan/sync/lock`，内容写成那个 id ③ 点同步 | 同步**正常开始**（不报锁错误）；日志里有 `Lock for app was created by this device … and never released (interrupted sync); replacing it.` |
| **TC-M2.1-07** 别人的锁仍然会被拒绝 | ① 再手工建一个 `lock`，内容写成别的标识（如 `some-other-device`）② 点同步 | 报错并中止，文案含**锁龄**与处理建议：`app 上有一个 x 秒前创建的同步锁，本次同步已中止。若两端都没有正在进行的同步…可删除对端工作区的 data/.siyuan/sync/lock 后重试（超过 5 分钟的锁会被自动忽略…）` |
| **TC-M2.1-08** 旧版残留的空锁 | 造一个**空内容**的 lock（模拟 M2 首版遗留）→ 立刻同步 | 5 分钟内仍会按"别人的锁"拒绝（无法判断归属）；等超过 5 分钟后再同步 → 被当成过期锁自动忽略并通过。**这就是你手机端那个残留锁的现状**（10:54 创建，早已过期，会被自动忽略并覆盖） |

> 说明：电脑端那份残留锁我在交付时已直接删掉了；手机端那份因为手机当时在休眠没连上，但它已超过 5 分钟，会被自动忽略。

## 5. 传输暂停（M2.3 新增）

| 用例 | 你做什么 | 会发生什么 |
|---|---|---|
| **TC-M2.1-17** 暂停生效 | ① 并发设 `1`（便于观察）② 同步一个改动较多的库 ③ 同步中点面板标题栏右侧的 **⏸** | 按钮变 **▶**；面板标题变 `同步已暂停`；下方提示 `点 ▶ 继续。注意：暂停超过 5 分钟后，锁会被判为过期，另一台设备可能开始同步。`；同时右上角弹提示「传输已暂停（正在进行的请求会先跑完）」。此后 `文件 i/M` **不再增长**（当前那一个请求会正常跑完，不会写坏文件） |
| **TC-M2.1-18** 继续 | 点 **▶** | 弹「传输已继续」；进度从暂停处继续推进，直到 `同步完成` |
| **TC-M2.1-19** 暂停不会被"记住"到下一次 | 暂停后让本次同步结束（或直接让它失败）→ 再点一次同步 | 新同步**正常开始**，不是一开局就暂停（代码在 done/failed 时自动清除暂停态）；暂停按钮只在同步进行中显示，空闲时看不到 |
| **TC-M2.1-20** 快捷键（可选） | `设置 → 快捷键` 搜「暂停/继续同步传输」→ 绑一个键 → 同步中按它 | 与点 ⏸/▶ 等效 |

> 说明：暂停的实现是"闸门"——被暂停时**不再启动任何新请求/新操作**；已经在飞的那一个请求会跑完（HTTP 请求中断可能留下半写文件，所以不硬取消）。这也意味着暂停不会丢数据，继续后从断点接着传。

## 6. 重复点击的提醒 + 取消传输（M2.4 新增）

| 用例 | 你做什么 | 会发生什么 |
|---|---|---|
| **TC-M2.1-21** 重复点击给明确提醒 | 同步进行中，再点一次顶栏云图标 | 弹一条 **7 秒**提示：`同步已在进行中 · 文件 137/520，本次点击已忽略（见右下角进度面板）。若长时间没有进展，可点面板上的 ⏹ 提前中断，或重载插件后再试。`（带当前进度数字）；同时**右下角进度面板被高亮 2.5 秒**；就算你之前点过 ✕ 关掉面板，它也会重新出现 |
| **TC-M2.1-22** 取消传输（提前中断） | 同步中点面板标题栏的 **⏹** | 弹「正在取消传输…」；面板标题变 `同步取消中…`、提示"等待当前请求结束；已传输的部分会保留"；随后（通常几秒内）标题变 `同步已取消`，顶部图标回到普通状态，toast 提示「同步已取消（已传输的部分会保留，下次同步从断点继续）」，约 15 秒后面板收起。**不会**报"同步失败"，也不会有锁残留 |
| **TC-M2.1-23** 取消后重跑能接着传 | 取消后立刻再点一次同步 | 正常开始新同步，**从断点继续**（已传完的文件不会重传，日志/面板上能看到 `文件 done/total` 迅速跳过已完成部分） |
| **TC-M2.1-24** 暂停中也能取消 | 先点 ⏸ 暂停 → 再点 ⏹ | 取消生效（自动解除暂停），行为同 TC-M2.1-22；不会卡在"暂停且取消中" |
| **TC-M2.1-25** 按钮状态自洽（M2.5 修复） | ① 同步中观察面板按钮 ② 点 ⏹ 后立刻再看 ③ 同步进入收尾（面板显示 `同步中 · 收尾处理`）时再看 | ① 传输阶段：⏸ 与 ⏹ 都在 ② 点 ⏹ 后：**两个按钮立刻消失**（不会出现"点了取消还能点暂停"） ③ 收尾阶段：两个按钮都不显示（此时已经没有数据可停）；若用快捷键在取消中调暂停，会提示「传输正在取消中，暂停已不可用」 |

> 为什么收尾阶段不给按钮：那个阶段只是刷新文件树/文档 + 写同步历史，数据早已传完 —— 在这里"取消"没法撤销任何东西，正是之前"点了终止却还能点暂停"看起来怪的原因。

> 取消的实现要点：排队的请求/操作**全部拒绝**，在飞的那个请求跑完（`getFileBlob` 支持真中止，走 SDK 的请求不可中止，所以等它自己超时/返回）；有明确检查点把取消传到 `syncHandler`，所以**不会出现"取消了却继续跑完还报成功"**；取消状态在每次同步开始时自动重置，重试逻辑也不会重试被取消的请求。
